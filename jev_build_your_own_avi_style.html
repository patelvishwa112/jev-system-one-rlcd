Build Your Own Jev (100% Local): Read Decisions Straight Out of an LLM

A hands-on walkthrough: turn a small open model into a fast, generation-free decision engine on your laptop — no server, no retraining. (A companion piece to our deep-dive, told the tutorial way.)

Runnable Code

Let me show you how to turn an open-source LLM into a fast, local decision engine — the useful part of what TypeSafe's Jev does — without retraining anything.

We will do it with a small model on a laptop. No GPU cluster, no API bill. By the end you will have a single Python function that reads decisions straight out of one forward pass.

One thing to set expectations upfront: this reproduces Jev's inference path. It does not reproduce Jev's weights or its RLCD calibration. We will come back to that honestly at the end.

Most LLM calls do not need generated text

Here is the thing most pipelines get wrong. Many LLM calls do not need newly written text at all. The application already knows the possible answers — it only needs the model to choose one.

Suppose a support ticket comes in:

"I was charged twice for the same subscription."

The application has to send it to exactly one of three teams: billing, technical support, or account access.

A normal LLM call asks the model to write an answer. It might return a sentence, a label, or a JSON object. Your code then waits for that text, parses it, and pulls out the team.

That is unnecessary work, because every valid answer is already known. A better way is to treat the request as a decision and ask the model for a score on each allowed answer, in one go:

one scoring request → a distribution
billing             0.91
technical support   0.06
account access      0.03

Billing wins — and your code can see how strongly it won. No sentence, no JSON, no parsing. That is the behaviour we are going to reproduce locally.

This is not the same as structured output

It is easy to confuse this with structured output (JSON mode, Outlines, Instructor), because both restrict what the application receives. But they do different work inside the model.

Structured output still generates. Under the hood the model writes the opening brace, the field name, the value, and the closing brace — one token at a time — and only then does your code read the field. The schema keeps it valid, but you still paid for a decode loop.

Scoring reads a distribution over answers you already know. And returning the whole distribution, not just the winner, is where it earns its keep. Look at two tickets:

Result 1Result 2
billing0.910.46
technical support0.060.44
account access0.030.10

Both pick billing. But the first has a clear winner, while the second is almost a coin flip. A model that only writes "billing" hides that from you. With scoring, your code can auto-route the first ticket and send the second one to a human. The threshold lives in your code, where you can test it and change it — not inside the model.

How an LLM picks its first token

To turn a model into a decision engine, it helps to remember what a normal generation step actually does.

Your prompt becomes token IDs. The model processes them and produces one vector for the next position. That vector has one number for every token in the vocabulary — for a Qwen or SmolLM tokenizer that is tens of thousands of numbers. Those numbers are logits; a bigger logit means the model prefers that token next.

In normal generation the server softmaxes that vector, picks a token, appends it, and runs the whole thing again for the next position. Over and over, until a stop token.

But for a bounded decision we only care about that first vector. We never need the second one.

Turn the decision into a one-token question

So we phrase the decision as a multiple-choice question and give each answer a short single-token label:

the prompt ends at "Label:"
Route the support ticket into exactly one category.

Ticket:
I was charged twice for the same subscription.

Allowed labels:
A = billing
B = technical support
C = account access

Answer with exactly one label.
Label:

The prompt ends at Label:. The next position is exactly where the model would write A, B, or C. So we run the prompt through the model once, and from that single next-token vector we do four small things:

  1. Find the token IDs for A, B, and C.
  2. Read the three logits at those positions.
  3. Ignore every other logit in the vocabulary.
  4. Softmax across just those three.

If the three logits were 8.2, 5.5, and 4.8, the restricted softmax gives roughly 0.91, 0.06, 0.03. Map those back to billing, technical support, and account access. The model never generated the answer — we read it.

The same trick covers all three of Jev's answer types:

  • Noul (yes/no): score two tokens, Yes and No → a single probability.
  • Choice (pick one): score the option letters → a distribution.
  • Score (rating): score the level letters, then take the expectation $\mathbb{E}[S]=\sum_i i\,p_i$ → a continuous rating.

One gotcha: labels must be exactly one token

This only works if each label is a single token. That is why we use letters, not the words.

A word like "billing" might be one token in one tokenizer and several in another; "technical support" is definitely several. Comparing multi-token phrases means scoring a sequence, which drags you back into generation. Single letters avoid all of that — the meaning still lives in the prompt, and the letter is just the token we inspect.

Watch one subtle bug: many tokenizers fold a leading space into the token, so "A" and " A" are different IDs. Always render the full prompt with the model's chat template, check what token actually comes next, and verify each label is exactly one token before you trust the scores.

Always give the model an exit

Restricted softmax puts all the probability on the labels you listed. If a security incident hits a router that only knows billing/technical/account, it still gets forced onto one of those three. Add an OTHER / ESCALATE option whenever the list might not be exhaustive.

Do it locally, no server

Avi Chawla's original walkthrough runs this through SGLang's /v1/score endpoint — the right choice for production, with continuous batching and KV-cache reuse. But you do not need a server to see it work. Here is the whole mechanism in plain Hugging Face transformers, one forward pass:

jev_scoring.py
import torch, torch.nn.functional as F

def score(model, tokenizer, prompt, letters):
    # each label must be exactly one token
    ids = []
    for L in letters:
        tok = tokenizer.encode(L, add_special_tokens=False)
        assert len(tok) == 1, f"{L!r} is not one token: {tok}"
        ids.append(tok[0])

    enc = tokenizer(prompt, return_tensors="pt").to(model.device)
    with torch.no_grad():
        logits = model(**enc).logits[0, -1, :]   # last position, whole vocab
    probs = F.softmax(logits[ids].float(), dim=-1)  # restricted softmax
    return dict(zip(letters, probs.tolist()))

Run it:

bash
python3 jev_scoring.py                                   # SmolLM-135M
python3 jev_scoring.py --model_id Qwen/Qwen2.5-0.5B-Instruct

That is the entire idea. The model loads once, you send a prompt, and you read three numbers back. No decode loop anywhere.

Now measure it

The reason to bother is speed, so let us measure it honestly on the same small model — SmolLM-135M on an Apple M1 laptop.

Routing one ticket, scoring took about 60 ms and generated 0 output tokens. Asking the same model to write a JSON answer took about 1,568 ms — roughly 26× slower. And the generated answer was broken: it wrote "choice": "1" (not even one of the options), then rambled until it ran out of tokens.

The gap grows with how much you generate, because scoring is one constant-cost pass while generation pays per token:

measured — bench_latency.py
output tokens:    1     10     25     50     75    100
generation (ms): 46    299    698   1378   2127   2794
scoring    (ms): ~51  ~51    ~51    ~51    ~51    ~51   (0 tokens, constant)
About 27 ms per generated token, versus a flat ~51 ms for scoring — a ~55× gap by 100 tokens.

One honest caveat, because it matters. A 135M model is fast but not smart. It actually mis-routes this ticket (it leans "frontend" at ~0.11 confidence — basically a guess). The mechanism is real and the speed is real; the accuracy needs a bigger, calibrated model. The JEV-CPU project measured this: balanced accuracy climbs from 0.44 at 0.6B to 0.69 at 2B to 0.81 at 4B. Same trick, better brain.

When to score, generate, or use structured output

Scoring is not a replacement for generation. It applies only when you fix the set of answers before inference. A quick rule:

  • Score when the output set is known and you just need a label plus its probability — routing, moderation, sentiment, a yes/no gate, a rubric rating.
  • Generate when the content is genuinely unknown — an email, a summary, code.
  • Structured output when you need arbitrary JSON with fields the model has to write (names, numbers, extracted spans). It still decodes token by token; it is not the same as scoring.

What we skipped, honestly

We reproduced Jev's inference path. We did not reproduce Jev itself.

A score of 0.91 only means billing got 91% of the probability mass among the three choices we offered. It does not mean the model is right 91% of the time — a raw pretrained model's confidence is not calibrated. Making the number trustworthy is a separate training step, RLCD (Reinforcement Learning for Calibrated Decisions), where the reward is an automated proper scoring rule against real outcomes. That is the part scoring alone does not give you, and it is the part worth reading about next.

But the inference path itself? You just built it, and it runs on a laptop.

That's a wrap

You turned an open LLM into a generation-free decision engine: one forward pass, read the option-token logits, restricted softmax, zero output tokens.
